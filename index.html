Sobre mí

Enfoque metódico de ingeniería: análisis riguroso, documentación exhaustiva y desarrollo seguro por defecto.

Ingeniería respaldada por disciplina y evidencia

Soy Sergio Daniel Florez Lopez, profesional orientado al desarrollo de software backend y al análisis de ciberseguridad. Concibo la seguridad no como una capa añadida al final del ciclo de vida, sino como un principio fundamental desde la primera línea de código y el diseño de la arquitectura de datos.

Me alejo de soluciones superficiales o mitos de ficción informática. Mi labor se fundamenta en principios sólidos: modelado metódico de amenazas, desarrollo de APIs RESTful resilientes, validación estricta de esquemas, reducción de superficie de ataque y automatización de controles técnicos reproducibles.

Cada sistema que construyo está pensado para operar bajo carga continua, resistir vectores de fallo o intrusión y mantenerse completamente documentado para auditorías y evolución en equipo.

Proyectos Seleccionados

Casos prácticos de desarrollo backend y seguridad aplicada, con problemas delimitados, soluciones técnicas y métricas medibles.

PRJ-01 BACKEND / AUTH

API Gateway Seguro & Servicio de Autenticación Centralizado

PROBLEMA:

Múltiples servicios backend internos expuestos sin una capa unificada de control de flujo, con riesgo de saturación por abusos de tráfico (DDoS de capa 7) y autenticación tokenizada inconsistente entre endpoints.

SOLUCIÓN TÉCNICA:

Desarrollo de un Gateway perimetral con middleware de Rate Limiting por IP/Token con almacenamiento en Redis, verificación asimétrica de tokens JWT (RS256), revocación en listas negras y sanitización estricta de payloads entrantes.

TECNOLOGÍAS:

Node.js Redis PostgreSQL JWT (RS256) Docker Linux
⚡
25 endpoints protegidos Sobrecarga de latencia < 9ms en pruebas de estrés

PRJ-02 AUTOMATIZACIÓN / DEVSECOPS

Pipeline Automatizado de Auditoría & Hardening CI/CD

PROBLEMA:

Fugas involuntarias de credenciales y dependencias desactualizadas con vulnerabilidades críticas (CVEs) detectadas solo tras llegar al servidor de pruebas, generando demoras en entregas.

SOLUCIÓN TÉCNICA:

Diseño de un pipeline automatizado de análisis estático (SAST), detección temprana de secretos (Gitleaks) y escaneo de capas de contenedor Docker (Trivy) con reglas de bloqueo estricto antes de cada merge a ramas principales.

TECNOLOGÍAS:

Python Bash GitHub Actions Trivy Gitleaks Docker
⏱️
Automatización de 3 tareas críticas Reducción del tiempo de auditoría de 4 horas a 12 minutos

PRJ-03 TELEMETRÍA / DEFENSE

Sistema Backend de Ingestión & Detección de Anomalías

PROBLEMA:

Falta de visibilidad centralizada sobre intentos de fuerza bruta, escaneo de directorios ocultos e inyecciones sobre endpoints REST repartidos en servidores independientes.

SOLUCIÓN TÉCNICA:

Construcción de un microservicio de recolección de eventos Syslog y logs HTTP, procesamiento con expresiones formales y reglas heurísticas de correlación temporal, disparando mitigaciones dinámicas en cortafuegos (UFW/iptables).

TECNOLOGÍAS:

Python (FastAPI) PostgreSQL Redis Linux Syslog Bash iptables

CASE_STUDY_REF: #SEC-2026-04 ESTADO: RESUELTO Y AUDITADO
ENTORNO: PRODUCCIÓN // BACKEND API

Caso Práctico: Detección y Remediación de Vulnerabilidad IDOR (Insecure Direct Object Reference) en API Multitenant

[01. VECTOR IDENTIFICADO]

Durante la auditoría de endpoints de facturación, se detectó que el endpoint PUT /api/v1/invoices/:id aceptaba un identificador numérico sin comprobar explícitamente en la base de datos si el organization_id del registro correspondía al claim verificado en el token JWT del usuario emisor.

[02. ANÁLISIS DE IMPACTO]

Riesgo de acceso indebido horizontal y modificación no autorizada de registros entre distintos clientes empresariales. Clasificación CVSS: 7.5 (Alta severidad en confidencialidad e integridad de datos).

[03. REMEDIACIÓN APLICADA]

Refactorización del middleware de datos en el backend para forzar un scope contextual inmutable: cualquier consulta o actualización incluye automáticamente la cláusula WHERE id = :id AND organization_id = :auth_org_id a nivel de capa de repositorio.

[04. PRUEBAS Y CIERRE]

Incorporación de 14 pruebas automáticas de integración que validan intentos de acceso cruzado entre tenants (esperando 404 Not Found o 403 Forbidden). Publicación del ADR correspondiente para el equipo de desarrollo.
